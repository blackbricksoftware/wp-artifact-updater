# Changelog

# v1.3.1 (2026-09-23)
- **Fixed: a release tagged `v1.0.4` was never offered, silently.** Versions are normalised on the way *out* now — into the `update_plugins_{$hostname}` answer, the pre-5.8 transient entry and the "View details" modal — not only inside our own comparison. Normalising the comparison alone was the trap: this library decided correctly that the release was newer, then handed core the raw string, and `wp_update_plugins()` re-ran `version_compare('v1.0.4', '1.0.3', '>')` itself, which is `false` because PHP reads the `v` as a pre-release-ish part. The library believed it had offered an update, WordPress disagreed, and nothing appeared or was logged. Only an artifact whose FILENAME carries no version reaches this path — `GitHubReleases` then takes the version from `tag_name` — which is why releases named `…-v2.8.3.zip` never tripped it, and why a repository publishing a fixed asset name would have hit it on its first update. A release cached by an earlier build is corrected on read rather than served raw until its TTL expires, and the displayed version is normalised deliberately: the modal should show the string core will compare
- Six tests covering it, each asserting on the entry handed to WordPress rather than on the internal newer/not-newer decision — the existing suite passed with the bug present precisely because it only checked the latter

# v1.3.0 (2026-09-22)
- **`flush()`** — forget the cached release so the next check really asks the host. WordPress asks at most twice a day and we answer from a six-hour cache, so a release published minutes ago can be invisible with nothing wrong anywhere. A consumer offering a "check now" button, or reacting to a credential being changed, needs this or it just re-reads the stale answer
- **`forceRecheck()`** — the whole "check now" dance in one call: clear our cached release, drop this plugin's entries from WordPress's update transient, and zero `last_checked` so `wp_update_plugins()` actually re-runs. Clearing either cache alone does nothing useful — ours is re-read from WordPress's, and WordPress's is refilled from ours. It is deliberately **not** `delete_site_transient('update_plugins')`, which every consumer writes first and which throws away what the site knows about every *other* plugin's updates; dropping only our own entries also stops a stale "update available" surviving a credential that has since been revoked

# v1.2.0 (2026-09-22)
- **Fixed: the Plugins screen showed no "Enable auto-updates" link.** WordPress only offers that toggle for plugins it considers updatable, and it decides that from the update transient: `WP_Plugins_List_Table` sets `update-supported` only for plugins present in `response` OR `no_update`. Returning `false` from the `update_plugins_{$hostname}` filter when a site was already current put the plugin in neither list (`wp-includes/update.php`: `if ( ! $update ) { continue; }`), so an up-to-date plugin looked like one that could never be updated — and auto-updates could not be switched on at all. The release is now always reported; core compares versions itself and files it as `response` or `no_update`. The pre-5.8 path does that placement itself, since nothing else will

# v1.1.0 (2026-09-22)
- **Credentials can be verified**, because the failure they cause is silent: a wrong, revoked or expired credential just means no release is ever found, which is indistinguishable from "you are up to date". `Updater::verify($source, $authorization)` makes one cheap request and returns `['ok', 'status', 'message']`, distinguishing a rejected credential from a host that did not answer — the remedies differ. Intended for validating a credential as it is entered, and for a "check this token" button later, since a token that worked in January can be revoked in June with nothing to show for it
- The Bitbucket verdicts name the fix rather than the symptom: 401 points at the **x-token-auth trap** (that form is for git over HTTPS; the REST API wants `Bearer <token>` — confirmed against a live repository, where Bearer returns 200 and `Basic base64("x-token-auth:<token>")` returns 401), 403 names the `repository` read scope, 404 names the repository it looked for

# v1.0.1 (2026-09-22)
- **Namespace renamed** `BlackBrickSoftware\WpUpdater` → `BlackBrickSoftware\WpArtifactUpdater`, matching the package name. Strictly a breaking change for anyone who required v1.0.0 — done immediately, while the only consumer is our own, rather than carried as a mismatch forever.

# v1.0.0 (2026-09-22)
- **WordPress updates for plugins distributed outside wordpress.org**, installing the release artifact a pipeline published — a zip in Bitbucket **Downloads** or a GitHub **release asset** — rather than a git tag archive. That distinction is the reason this exists: a composer-based plugin's source tree has no `vendor/`, so installing a tag archive produces a plugin with no autoloader that fatals on activation. [plugin-update-checker](https://github.com/YahnisElsts/plugin-update-checker) can't be pointed at Downloads (`BitBucketApi::getDownloadUrl()` is hard-wired to `/get/<ref>.zip`, and unlike its GitHub and GitLab classes it has no release-asset support), and its auth header is gated on that same `/get/` prefix, so rewriting the URL yields a 401
- **`Source` interface** with two implementations, each supporting public and private repositories: `BitbucketDownloads` (private by default) reads the Downloads list and picks the highest version by comparison rather than list order, so `2.10.0` beats `2.9.0`; `GitHubReleases` (public by default) reads the latest release's assets and takes the version from `tag_name` when the filename has none, which is the common case for workflows publishing a fixed asset name
- **The credential is an Authorization header value supplied by a callable**, never a username/password pair and never read from storage the library chose. Consumers resolve it however they like — environment variable, constant, their own settings — so Bitbucket repository access tokens (`Bearer`), app passwords (`Basic`) and GitHub tokens all work without the library knowing the difference
- **Credentials are never sent to the storage host.** Release hosts answer a download URL with a 302 to a signed URL on separate infrastructure; following that with an `Authorization` header attached would hand the credential to a third party and be rejected by it, since the signature is the authentication. Each source resolves its own redirect and hands WordPress a URL that needs no credential
- **Off by default where it can't work, and never forced.** A private source with no credential registers no hooks and makes no HTTP requests — which is what keeps it out of the way on composer-managed installs, where the deploy owns the plugin version. A public source can't use that signal, so `enabled` is a callable consumers can supply. No `auto_update_plugin` filter is registered anywhere: updates are offered and each site opts in, because an authentication plugin that installs a bad release unattended across every site locks everyone out at once
- **A leading `v` is stripped before comparing versions.** `version_compare('v2.0.0', '2.0.0')` is `-1` in PHP, so a plugin whose header carries the prefix would otherwise be offered the same version it already runs, forever
- Results are cached in a site transient (6 hours by default, 15 minutes after a failure) so a bad minute at the release host doesn't mean an HTTP request on every admin page load. WP 5.8+ uses the `Update URI` host filter, older sites the update-plugins transient; `plugins_api` is answered locally so core never asks wordpress.org about a plugin it has never heard of
- `src/V1/` with PSR-4 mapping `BlackBrickSoftware\WpArtifactUpdater\` → `src/`, so a future breaking change is a new `src/V2/` directory and nothing else
- 42 tests, no PHPUnit and no WordPress — `php tests/run.php` runs in a bare PHP image
